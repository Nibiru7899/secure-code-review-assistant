# Secure Code Debugging and Review Assistant — Implementation Plan

## Goal and delivery boundaries

Build the complete Case Study 4 local application in D:\TataTech: authorized C/C++ indexing, cited code explanations and summaries, diagnostic interpretation, evidence-backed candidate reviews, reviewer decisions, historical findings, PostgreSQL, and Docker. Preserve the fixed stack in AGENTS.md. The application never edits reviewed code or merges/releases it.

The application may read and analyze authorized source repositories and imported engineering evidence. It does not operate the software-development lifecycle around those repositories.

Build only what is needed to implement, secure, validate, or demonstrate Case Study 4.

Excluded: Git-diff review, changed-function review based on Git, PR bots/comments, CI AI-review jobs, CI-specific CLI, branch manipulation, automatic fixes/commits/merges/releases, agents, graph databases (including Neo4j), Kubernetes, and autonomous debugging.

The application may invoke explicitly configured deterministic analysis tools, such as Cppcheck, against authorized captured source scope. It must not execute repository scripts, build commands, hooks, or commands embedded in source or imported logs. Imported compiler/build/runtime/CI logs are evidence only; importing them does not trigger pipelines.

Deliver three checkpoints. At each checkpoint demonstrate actual success and failure output, publish a reproducible verification report, and wait for explicit user approval before the next phase. This plan authorizes no application implementation by itself.

## Checkpoint 1 — Secure local foundation and retrieval

1. Verify Windows Python/Cppcheck availability and optional Git metadata support, NVIDIA hardware and Ollama installation. Download the chosen artifacts during setup, record their identities, then verify local API response, actual GPU use, request duration, and an 8192-token configuration. Start with qwen2.5-coder:7b Q4_K_M; use 3b only after a measured memory failure and record the change. No model stability claims before live checks.
2. Create the minimal Python project, configuration example, dependency lock, test harness, and smoke-test script. Keep data under a configurable local data directory outside scanned repositories. Services use loopback. Local credentials map to identities and repository/path permissions; tests use synthetic credentials. Secrets stay out of version control and logs.
3. Build demo_ecu with headers/cross-file calls and fixture-labelled safe and defective functions. Start with enough examples for 20 retrieval questions; expand to 20 defective and 10 safe functions by Checkpoint 2. Ground truth lives outside retrieved source so the model cannot read expected answers.
4. Implement approved-root registration and permission checks before scanning. Enforce extension/size/ignored-directory rules, skip secrets/binaries/generated output, reject root escapes, and report per-file skip/failure reasons. Test Windows junction behavior explicitly.
5. Use Tree-sitter C/C++ to extract qualified symbols, paths, language, source ranges and content. Distinguish overloaded symbols with signature/file metadata. Fall back to bounded file chunks on parsing failure and expose parser status. Preserve declarations/header context needed for retrieval without pretending to build a complete call graph.
6. Produce deterministic content-based snapshots for ordinary local directories and Git working trees. Git commit metadata may supplement provenance when available but must never be required. Store a manifest, original source evidence and content hashes locally. Embed code/rules on CPU using the pinned Jina artifact; persist separate Chroma collections. Stage index generations and switch the active snapshot only on success; garbage-collect obsolete generations after successful publication while preserving snapshots referenced by stored reviews.
7. Implement exact file/symbol lookup plus bounded semantic code/rule retrieval. Apply authorization and snapshot filters before returning content. Resolve ambiguity explicitly; non-existent targets return a clear result. Include evidence IDs and complete provenance.

Acceptance: local model/GPU smoke checks pass; 20 fixed retrieval queries are evaluated; every exact lookup resolves correctly or reports ambiguity/absence; unchanged indexing is idempotent; changed/deleted source is replaced without stale active chunks; failed reindex preserves the previous index; parser failure and unreadable files are explicit; unauthorized reads are blocked. Verify indexing/snapshots/retrieval for ordinary directories and Git working trees and changed/deleted files through re-indexing. Inspect at least five contexts and restart to verify persistence. Report semantic top-k performance rather than inventing a target achieved by the chosen model.

## Checkpoint 2 — Review, explanations, and diagnostics

1. Add Cppcheck execution with argument arrays, bounded time/output, version capture, XML normalization and snapshot-linked finding IDs. Treat missing executable, timeout, malformed output and process failure separately from a successful empty result. Record analyzed scope and limitations. Analyze a captured snapshot rather than changing live source midway through a run.
2. Build the common context pipeline: identity/permissions → snapshot evidence → relevant analysis → bounded prompt → local model → Pydantic parsing → evidence validation → result. Reserve 1536 output tokens and 512 budgeting tokens in the 8192-token window. Reject overflow or split into explicit partial reviews. Review large files through bounded units and report coverage.
3. Require structured output and at most one corrective retry. Use evidence IDs for source, rules and analyzer findings. Verify path, function, line ranges, source quotes, retrieved rule IDs, analyzer correspondence and snapshot identity. Invalid output never becomes a validated finding. Backend-derived support labels distinguish analyzer-supported from AI-only candidates.
4. Implement review endpoints, cited function/module explanations and code Q&A, and imported compiler/build/runtime/CI-log interpretation. All requests include an authorized repository and snapshot. Code Q&A uses the existing `/qa` endpoint; explanation endpoints retain their optional questions. Imported diagnostic evidence records origin and whether association is verified; unsupported source mappings are rejected. Include evidence-supported dependency/control-flow summaries, candidate null-pointer, boundary, resource, and state issues, security-focused observations, coding-standard explanations, and secure-coding recommendations. Root-cause hypotheses remain visibly qualified. Use original/demo rules only: do not download, copy, embed, or reproduce actual MISRA rule text or claim MISRA compliance. MISRA-oriented support is a future capability only if approved/licensed guidance is explicitly supplied.
5. Return an envelope containing run ID, snapshot, outcome, dependency statuses, coverage, limitations and evidence-backed output. Use CANDIDATES, NO_SUPPORTED_FINDING, INSUFFICIENT_EVIDENCE, or FAILED. Preserve findings separately from run outcomes. Failure results must not resemble a successful clean review.
6. Expose GET /health; POST /repositories/index; GET /repositories/{id}/status; POST /review/function; POST /review/file; POST /explain/function; POST /explain/module; POST /diagnostics/interpret; GET /findings; GET /findings/{id}. Add authorized file/function listing for selectors. Use 401/403 for identity/access failures, 404 for missing authorized targets, 409 for snapshot/target conflicts, and 422 for invalid input. Dependency failure returns explicit failed/degraded run details.
7. Persist minimal repositories, snapshots, analysis runs and findings in SQLite now so findings endpoints work; Checkpoint 3 extends the reviewer workflow. Preserve original outputs and validation diagnostics locally without routine prompt/source logging.

Acceptance: rerun Checkpoint 1 tests; evaluate 20 defective and 10 safe functions using fixed labels; report precision, recall, false positives, malformed output, rejection rate and latency. Separate synthetic-client tests from live Ollama results. Test fabricated files/lines/quotes/rules/analyzer IDs, unrelated-warning support, diagnostic/repository injection, denied retrieval, stale snapshots, model/analyzer failure, and context limits. Inspect ten prompts/findings plus explanation and diagnostic outputs; verify review works for both ordinary local directories and Git working trees. Zero unauthorized content reaches the model and zero invalid citations reach validated output in the test corpus; semantic accuracy remains measured and human-reviewed.

## Checkpoint 3 — Human review and delivery

1. Build Streamlit selectors and controls for indexing, review, explanation, diagnostic import. Show captured source, rules, analyzer evidence, interpretation, support, limitations and statuses separately. Communicate partial/failed reviews clearly.
2. Add authenticated Accept/Edit/Reject through POST /findings/{id}/review. Store immutable original findings and append-only reviewer revisions/actions. Revalidate changed references, persist timestamps and provenance, and expose authorized history. GET /analysis-runs/{id}/report exports structured JSON with evidence references and dispositions. Approved historical findings may be retrieved as labelled evidence, never instructions.
3. Extend the storage schema with users, permissions and review actions; migrate SQLite data to PostgreSQL with stable IDs/relationships. Back up SQLite before migration. Verify representative query equivalence and a rollback procedure using isolated fixtures; retain SQLite as the tested native pilot option.
4. Containerize FastAPI and Streamlit with persistent local Chroma storage and PostgreSQL. Keep Ollama host-managed. Use read-only repository mounts, separate writable data volumes, health checks and documented host connectivity. No unnecessary Chroma server or GPU container requirement.
5. Write README-only native and Docker setup procedures, offline runtime guidance, startup/shutdown order, reset/rebuild instructions, backup/restore, credential configuration and benchmark reproduction. Record artifact versions and measured results. Document production encryption/private-network requirements rather than declaring enterprise readiness.

Acceptance: rerun all previous deterministic tests and live evaluations; verify UI success/degraded/failure flows, reviewer revisions/history after restart, unauthorized report/history access, PostgreSQL migration/rollback, Docker read-only mounts, persistence, database failure and vector rebuild. Follow the README from a clean project/dependency environment and report any untested fresh-machine assumptions. Demonstrate a known defect, safe function, diagnostic interpretation, cited Q&A, module summary and persisted reviewer action. Record productivity pilot baselines/results when available; mark defect leakage or throughput unmeasured when no real pilot exists.

## Measurement and remaining factual checks

Record dataset and artifact identities, context settings, token counts, analyzer version, hardware, cold/warm latency and failure rates. Do not change retrieval/model settings without a baseline comparison. No universal accuracy or prompt-injection immunity claims.

Ollama installation, available GPU/VRAM, system RAM, tool versions and model feasibility remain to be verified.
